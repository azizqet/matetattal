# الأمان — فزّاع

## الضوابط المطبّقة
| المجال | التنفيذ | التحقق |
|---|---|---|
| المصادقة | هاتف + كلمة مرور فقط عبر Supabase Auth (Admin API رسمي، بدون حسابات بريد وهمية). كلمات المرور مُجزّأة لدى Auth. سياسة 8 أحرف + حروف وأرقام | `tests/backend/auth.test.ts` |
| منع OTP/SMS | التسجيل المباشر على Auth API معطّل؛ خطاف `send_sms` يرفض كل OTP | اختبار «blocks direct sign-up and OTP» |
| محاولات الدخول | قفل 15 دقيقة بعد 5 محاولات فاشلة لكل رقم + 30 لكل IP، مطبّق في `auth-login` وفي خطاف Auth (لا يمكن تجاوزه بالاتصال المباشر) | اختبار «locks the account after 5 failures» |
| عدم كشف الحسابات | نفس الرد للأرقام غير المسجلة ولطلبات الاستعادة | اختباران |
| الحسابات الموقوفة | رفض الدخول + حذف الجلسات فوراً + رفض كل RPC | اختبار «refuses suspended accounts» |
| الصلاحيات | RLS على كل الجداول؛ إلغاء كل صلاحيات anon/authenticated ثم منح دقيق؛ أعمدة الملف الشخصي القابلة للتعديل محصورة (الاسم، اللغة، الصورة) | `security.test.ts` (12 جدولاً لـ anon، تصعيد صلاحيات، أعمدة محمية) |
| الدوال | قائمة سماح صريحة (migration 0800). الدوال الداخلية (finalize_order, notify_user, rate limits, حذف الحساب…) غير قابلة للاستدعاء من العميل | اختبار «internal helpers are not callable» — **اكتُشفت ثغرة هنا وأُصلحت**: الإعدادات الافتراضية في Supabase كانت تمنح `anon` تنفيذ الدوال الجديدة |
| العمليات الحساسة | كل تغيير حالة/مال في دوال خادم مع أقفال صفوف؛ لا كتابة مباشرة على orders/offers/ledger/drivers | اختبارات التزامن والتلاعب |
| الأرصدة | سجل append-only (مشغّل يمنع UPDATE/DELETE)، رصيد مخزّن يُحدَّث بمشغّل فقط، فهرس فريد يمنع تكرار العمولة | اختبارات المالية |
| الإدارة | أدوار owner/admin/finance/support؛ كل إجراء إداري يُسجّل في `audit_log` (غير قابل للتعديل)؛ عرض مواقع المناديب يُسجّل أيضاً | `admin role boundaries` |
| التخزين | حاويات خاصة للمستندات والإيصالات وملفات الطلبات؛ مسارات مقيدة بهوية المستخدم/المشاركين؛ روابط موقّعة قصيرة (5 دقائق في اللوحة)؛ حدود حجم وأنواع ملفات؛ إزالة EXIF/GPS بإعادة ضغط الصور | اختبارات التخزين |
| الخصوصية | لا يُخزَّن موقع المندوب إلا أثناء طلب نشط؛ المناديب لا يرون هاتف المستلم/العنوان الكامل قبل القبول | اختبارات «without private data» و«location only during active order» |
| معدلات الطلبات | تسجيل، دخول، طلبات، عروض، رسائل، إيصالات، تذاكر، أكواد خصم | اختبار «rate limits abusive offer spam» |
| المفاتيح | لا مفاتيح سرية في التطبيق أو اللوحة (فحص الحزم المبنية). service role يُستخدم فقط داخل Edge Functions. ملفات `.env` مستثناة من git | فحص الأسرار |
| تخزين الجلسة | Keychain/Keystore عبر expo-secure-store (مقسّمة)؛ اللوحة تستخدم sessionStorage | — |
| الويب | CSP وX‑Frame‑Options في `apps/admin/public/_headers`؛ حماية CSV من حقن الصيغ | — |

## نتائج الفحوصات
- `npm audit --omit=dev`: لوحة التحكم 0، الاختبارات 0، تطبيق الجوال 3 «moderate» في `minimatch` عبر `@expo/fingerprint` (أداة وقت البناء، لا تُشحن داخل التطبيق ولا تعالج مدخلات المستخدم). لا يوجد إصلاح دون كسر توافق Expo؛ يُراجع عند تحديث SDK.
- `supabase db lint`: لا أخطاء؛ تحذيرات فقط عن تحويل نص→enum ضمني ومعامل غير مستخدم (سلوك صحيح ومختبر).
- فحص الأسرار في الملفات المتتبعة والحزم المبنية: لا مفاتيح سرية.

## توصيات قبل الإنتاج
1. تفعيل **Leaked password protection** و **MFA للمشرفين** (عند توفره) في Supabase Auth، وتفعيل SSL enforcement و Network restrictions لقاعدة البيانات.
2. تقييد مفتاح Google Maps بالحزمة والبصمة.
3. تشغيل `get_advisors` (Security/Performance) في لوحة Supabase بعد الرفع ومعالجة أي ملاحظة.
4. اختبار اختراق مستقل قبل الإطلاق التجاري.
